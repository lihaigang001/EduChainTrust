# Security and scope

EduChainTrust v1.12.0 is a research prototype for synthetic local demonstrations. The API fails closed without configured tokens and trusted Ed25519 issuer keys. The issuer role signs with its active method and anchors only its own credentials bearing that active method; previously anchored old-key evidence remains verifiable while the old public key is retained; revocation is limited to the owning issuer or administrator. The composite verifier checks the signature, trust registry, credential time, issuer/anchor attribution, digest, and status.

On POSIX, startup walks the path to each local JSON token configuration and issuer PEM through checked directory descriptors. It refuses symlink components and group/other writable directory components, except root-owned sticky temporary directories, and reads the regular file through its checked descriptor. Every component and final file must be owned by root, the service UID, or an explicitly configured trusted UID. `EDUCHAINTRUST_TRUSTED_CONFIG_UID` permits one additional numeric UID for a known host operator when a root-run container reads bind-mounted files; do not set it to an untrusted user. Token configuration and private keys are rejected when any group/other permission bit is set. Provisioned files use mode 0600 in a mode 0700 directory. These checks do not validate Windows ACLs, secret exposure through backups or process memory, or protection against another process with the same user identity. Credential JSON requests are limited to 256 KiB and 64 nested containers; this does not replace an external rate limiter.

This is not a production identity or credential authority. API keys in a local JSON file are not institutional key management, and this project does not implement institutional onboarding, managed key rotation, HSM storage, TLS termination, rate limiting, privacy retention rules, audit-log export, or distributed consensus. Do not expose the dashboard or API to untrusted networks and do not use real learner data. The Docker Compose example binds only to loopback and uses a restricted build context that excludes local secrets. Production deployment requires an independent design and security review.

Report security issues privately to the maintainer at lihaigang02292@qqhru.edu.cn. Do not include sensitive learner data in public reports.

## v1.12 identity and legacy boundary
New API anchors require canonical, 64-byte Ed25519 proof values and unique issuer/credential ID pairs. Old v1.11 proof encodings are accepted for verification only when the submitted bytes exactly match the existing historical row. Equivalent encodings of the same signature are checked against old digests at anchoring. Legacy hashes cannot reveal credential IDs, so a re-signed or otherwise changed historic credential with the same ID can evade that legacy lookup. The low-level store does not infer the credential ID or alternate hashes: callers outside the API must supply these values themselves. Back up existing databases before migration.
